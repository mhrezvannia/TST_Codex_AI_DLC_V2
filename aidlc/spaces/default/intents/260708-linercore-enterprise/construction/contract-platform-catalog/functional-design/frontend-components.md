# Frontend Components - contract-platform-catalog

## Source Context

This artifact consumes `unit-of-work.md`, `unit-of-work-story-map.md`, `requirements.md`, `components.md`, `component-methods.md`, `services.md`, and `functional-design-questions.md`.

The accepted Functional Design answer is to include a lightweight read-only contract health/catalog surface in Enterprise Web or an operations route. It provides evidence for contract readiness and failure triage. It must not become a domain business workflow owner.

## Component Scope

The frontend surface is read-only and operational:

- Show contract catalog status by seam, service, protocol, story, and version.
- Show validation and compatibility reports.
- Show failing seams and owner mobs.
- Link to source contract files and generated reports where available.
- Support local runtime and CI evidence review.

It does not edit contracts, pricing rules, booking rules, movement rules, D&D rules, or service data.

## Component Responsibilities

### ContractHealthRoute

Responsibilities:

- Fetch latest `ContractHealthSnapshot`.
- Apply route-level auth/capability checks from Identity/Enterprise Web patterns.
- Render summary, filters, table, and details.
- Display stale or unavailable catalog evidence as non-green status.

### ContractHealthSummary

Shows:

- Overall status: green, amber, red.
- Count of executable contracts.
- Count of markdown-only/non-executable contracts.
- Count of breaking compatibility results.
- Count of stale validation runs.
- Last local and CI validation timestamps.

### ContractSeamFilterBar

Filters:

- Service owner.
- Consumer.
- Protocol.
- Contract kind.
- Status.
- Story/requirement.
- Bolt.

### ContractSeamTable

Rows:

- Seam id.
- Provider.
- Consumer.
- Required artifacts.
- Latest version.
- Syntax status.
- Compatibility status.
- Pact/message-pact status.
- Schema Registry status.
- Owner mob.

### ContractFailurePanel

Shows blocking failures first:

- Missing executable artifact.
- Metadata failure.
- Syntax validation failure.
- Breaking compatibility.
- Pact/message-pact failure.
- Schema Registry failure.
- Stale result.

Each failure names owner, source path, failing rule, remediation, and affected downstream units.

### ContractArtifactDrawer

Shows:

- Contract metadata.
- Semantic version history.
- Linked requirements and stories.
- Canonical examples.
- Positive and negative fixtures.
- Source and report links.

## Data Contract For UI

The UI consumes a read-only API or static JSON report generated by the contract platform:

| Field | Meaning |
|---|---|
| `snapshotId` | Unique health snapshot id. |
| `generatedAt` | Snapshot generation timestamp. |
| `overallStatus` | `green`, `amber`, or `red`. |
| `seams[]` | Contract seam status rows. |
| `failures[]` | Blocking and warning findings. |
| `artifacts[]` | Source files, examples, fixtures, and report links. |

The UI must not infer green status from missing data. Missing or stale data renders amber/red according to catalog policy.

## Interaction Flow

1. User opens Operations or Contract Health route.
2. Route loads latest snapshot.
3. Summary shows overall status and stale/failure counts.
4. User filters by service, protocol, status, or story.
5. User opens a failing seam.
6. Failure panel shows validator, path, rule, owner, and remediation.
7. User opens artifact drawer for examples and report links.

## Validation Rules

- Denied-path tests verify unauthorized users cannot view contract health.
- Read-only tests verify no editing controls exist in this unit.
- UI integration tests use the generated snapshot schema, not hardcoded mock-only business results.
- Empty or missing snapshot state must render a visible non-green state.
- UI routes must preserve Enterprise Web density and operational scanning patterns from `components.md` and `services.md`.
