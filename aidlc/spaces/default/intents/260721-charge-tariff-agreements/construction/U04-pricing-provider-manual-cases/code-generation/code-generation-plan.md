# Code Generation Plan — U04 Pricing Provider and Manual Cases

**Approved 2026-07-28.** Approval selection:
`Approve Plan (Recommended)`.

## Outcome and Boundaries

Implement U04 inside the existing `charge-agreement-service`, `apps/charge-agreements`, and bilateral pricing contract. The result must make `POST /pricing-requests` the real agreement-first/complete-tariff authority, persist byte-stable terminal receipts and one OPEN manual case for missing or ambiguous authority, and expose authorized read-only manual evidence.

This plan implements FR-301–FR-307, FR-401–FR-407, FR-604/FR-606, NFR-002–NFR-005, NFR-009/NFR-010, and U04 support for US-06, US-07, US-10, US-11, US-12, US-13, and US-14.

Binding ownership and preservation rules:

- Preserve U01 Rate domain/repositories and the U01-owned immutable Flyway files `V1__charge_baseline.sql` through `V4__pricing_terminal_evidence.sql`.
- Preserve U02 Charge base path, signed-session/BFF assertion, normalized errors, and route-preservation seams.
- Preserve U03 Agreement domain, W2-only authority model, exact rate links, lifecycle, events, and disabled outbox relay posture.
- Preserve Booking ownership of pricing orchestration, typed snapshots, `MANUAL_PRICING_REQUIRED`, repricing, and Booking UI; U04 changes only the synchronized provider/consumer contract fixtures.
- Preserve manager port `8088`; runtime work targets only the isolated Wave A edge at `18088` through `scripts/wave-a-compose.mjs`.
- Do not edit `packages/ui`, shared shell/navigation, design-system master, typography, palette, or another domain's pages.
- The manual surface shows automatic-pricing failure evidence and the responsible Pricing Analyst role only. It must not add an amount, quote, assignment, approval, resolution, closure, or retry/reprice action.

## Current-Source Starting Point

- The checked-in Graphify snapshot predates the active U01–U03 dirty-worktree implementation. Current source therefore wins after Graphify/codebase-memory orientation.
- `ChargeAgreementApplicationService.requestPricing` still delegates to legacy mutable `CustomerAgreement`/commodity/specificity logic, hashes a pipe-delimited string, reconstructs terminal results, and records cases outside atomic terminal completion.
- `PricingApiController` still defaults `X-LinerCore-Actor-Id` to `booking-service`, derives `bookingRef` from request ID, emits `local-correlation`, and has only the legacy response/error fields.
- `PricingRequestRepository`/`JdbcPricingRequestRepository` deserialize `PricingResult` and do not write the V4 terminal HTTP/schema/request/case columns or exact public response bytes.
- `ManualPricingCaseRepository`/`JdbcManualPricingCaseRepository` only upsert by case ID; they do not implement canonical create-or-get, authorized list/detail, legacy-winner reuse, or receipt/case atomicity.
- U01 Rate and U03 W2 Agreement repositories do not yet expose the bounded pricing-candidate reads required by U04.
- U02 browser routes `app/api/manual-cases/**` exist, but `MANUAL_CASE_POLICIES` currently targets the wrong backend paths/media/query vocabulary. No Charge manual-pricing page exists.

## Approval-Sensitive Tradeoffs

1. **Migration/index tradeoff — default is no migration.** U04 consumes the U01-owned V4 schema unchanged. The approved design accepts a bounded PostgreSQL sort for `opened_at DESC NULLS LAST, case_id ASC` over the existing status-leading index and gates it on 10,000 cases, 4 MiB work memory, no spill, page size 100, and p95 ≤750 ms. If that executable plan fails, implementation must stop and request schema-owner approval for an additive forward migration (normally a U01-owned V5); U04 must not edit V1–V4 or silently author a migration.
2. **Pricing service identity tradeoff — bilateral approval may be required.** The current provider's default actor is prohibited. U04 can add a fail-closed Charge inbound service filter/config, but if the existing Booking client does not already send the selected trusted identity credential, the minimal header/config change crosses into Booking consumer ownership and requires explicit Charge-provider/Booking-consumer approval. Until approved, keep that integration cell blocked; do not retain the default actor.
3. **Contract evolution tradeoff — additive schema, strict runtime.** New v1 properties remain optional in OpenAPI so old consumers validate; every W2 provider 200 emits them all, old absence selects legacy decode, and partial enrichment is malformed. U04 owns provider and synchronized fixtures, while U05 owns Booking implementation. A breaking field/type/required-set change requires a separate contract-version decision.
4. **Manual evidence tradeoff — evidence, not workflow.** The scope intentionally leaves cases OPEN and read-only. Operational ownership is shown through the Pricing Analyst role and evidence/correlation only; adding amount entry, assignment, approval, resolution, closure, or automated repricing is a new product workflow requiring separate approval.
5. **UI integration tradeoff — no local shell workaround.** The Charge page can be complete while DS-03 no-ribbon evidence remains blocked on W2-02's integrated route-metadata seam. U04 must not hide the ribbon with local CSS, fork the shell, or edit `packages/ui`.
6. **Event/runtime tradeoff — no new asynchronous pricing path.** Pricing remains synchronous and produces no Kafka event. Existing U03 agreement events and disabled relay are regression surfaces only. Introducing pricing events, an async workflow, new service, cache, cloud resource, or production deployment path requires a separate architecture/scope approval.
7. **Rollback tradeoff — forward repair after durable U04 state.** A previous image is eligible only in the exact zero-state drained/read-only compatibility cell. Otherwise forward repair is mandatory; destructive reset, down migration, or a write-capable old image is not an acceptable rollback.
