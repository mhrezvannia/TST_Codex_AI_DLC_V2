# Discovered Rules

Derived from code-structure.md, technology-stack.md, dependencies.md, code-quality-assessment.md, architecture.md, and business-overview.md plus the guided interview.

## Mandated

ALWAYS use a short-lived program intent branch from the explicitly protected integration baseline.

ALWAYS make final integration mode an explicit program-owner decision when written rules and observed history conflict.

ALWAYS write focused tests alongside changes and reproduce defects with a failing regression test when practical.

ALWAYS require canonical integrated live proof, demo safety, and mandated audits in addition to static and component checks for UI closure.

ALWAYS use scripts/wave-a-compose.mjs and the linercore-wave-a project for W2-02 live acceptance.

ALWAYS use @erp/ui tokens and applicable primitives for shared presentation, documenting and testing any native-semantic exception.

ALWAYS preserve service, BFF, authenticated-shell, and package ownership boundaries during design-system closure.

## Forbidden

NEVER infer a universal squash or no-fast-forward merge rule solely from local git history.

NEVER invent a coverage percentage, scanner pass, deployment environment, or branch-protection guarantee without executable evidence.

NEVER use the protected linercore-shared-platform manager demo as a closure acceptance target.

NEVER treat package tests, detached module pages, screenshots alone, or the historical W1 waiver as canonical live proof.

NEVER create a module-local theme, duplicate authenticated shell/navigation, or second frontend for W2-02.

NEVER replace correct native semantics merely to satisfy wrapper-counting; exceptions must remain explicit and testable.
