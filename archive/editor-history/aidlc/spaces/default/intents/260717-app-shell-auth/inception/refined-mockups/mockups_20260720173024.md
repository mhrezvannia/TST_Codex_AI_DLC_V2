# Refined Mockups - W2-01 App Shell and Auth

## Source Context

These refined mockups consume `wireframes.md`, `user-flow.md`, `stories.md`, `requirements.md`, and `team-practices.md`. They refine the approved W2-01 shell/auth/Booking path only and do not define W2-02 design-system foundation or W4-01 broad module migration.

## Screen A - Protected Entry

Route candidates: `/` for shell landing and `/booking` for Booking, or `/app` and `/app/booking` if application design chooses a namespace. The mockup remains route-agnostic until application design locks the path.

State sequence from `user-flow.md`:

1. Browser opens protected shell URL through Nginx.
2. No session state renders a brief loading or redirect status.
3. User is redirected to existing auth/Keycloak.
4. Successful callback returns to shell landing.

Visual specification:

- Main content is not visible before authorization succeeds.
- Redirect state uses a single heading, short status text, and no raw token or internal error display.
- Focus moves to the auth flow's first actionable control when sign-in UI is shown.

## Screen B - Authenticated Shell Landing

Purpose: satisfy US-01 and FR-01 by making the shell the first authenticated product surface.

```
+--------------------------------------------------------------+
| LinerCore                         Search        User menu v   |
+------------------+-------------------------------------------+
| Navigation       | Breadcrumbs: Home                         |
| > Booking        |                                           |
|   Reference Data | h1 LinerCore                              |
|   Charge         | Section: Operational start                |
|   Movement       | Primary tile/link: Booking                |
|                  | Secondary modules: Not mounted yet        |
+------------------+-------------------------------------------+
```

States:

- Loading: shell chrome skeleton plus "Checking session" text.
- Ready: Booking available for authorized users; non-mounted modules marked "Not mounted yet" or external-link text.
- Session expired: redirect status then auth flow.
- Error: recoverable message with correlation id where available.

## Screen C - Booking List Mounted in Shell

Purpose: satisfy US-04 and FR-04 by preserving Booking list/create behavior inside shell chrome.

```
+--------------------------------------------------------------+
| LinerCore                                      User menu v    |
+------------------+-------------------------------------------+
| Navigation       | Breadcrusmbs: Home / Booking                |
| > Booking        | h1 Booking                                |
|   Reference Data | [New booking] [Search] [Filters]          |
|   Charge         | Showing recent bookings                   |
|                  | Table/Card list with status and actions   |
+------------------+-------------------------------------------+
```

States:

- Authorized empty: Empty state says no bookings are available and keeps "New booking" visible if create is allowed.
- Authorized populated: table on desktop; cards on mobile with booking reference, status, route summary, and primary action.
- Loading: content-shaped skeleton, not a raw spinner-only page.
- Error: inline error with retry and correlation id.
- No permission: switch to Screen E inside the same shell frame.

## Screen D - Booking Detail or Action Evidence

Purpose: satisfy US-02 and US-04 by making subject propagation visible to QA without exposing tokens.

```
+--------------------------------------------------------------+
| LinerCore                                      User menu v    |
+------------------+-------------------------------------------+
| Navigation       | Breadcrumbs: Home / Booking / BK-123       |
| > Booking        | h1 Booking BK-123                         |
|                  | Summary, route/equipment/status           |
|                  | [Create/Confirm action as available]      |
|                  | Evidence                                  |
|                  | Subject: local.booking.user               |
|                  | Actor header: session-derived             |
|                  | Authorization: allowed or denied          |
|                  | Correlation: <id>                         |
+------------------+-------------------------------------------+
```

States:

- Allowed action success: success message in an `aria-live` region; evidence panel shows real subject and correlation id.
- Denied action: no data mutation; denied message names the requested action and gives request-access/back actions.
- Missing subject: fail-closed message; no retry as `local-user`.
- Confirm unavailable: create/detail proof still proceeds and confirm is labelled as unavailable rather than hidden as a failure.

## Screen E - Access Denied Inside Shell

Purpose: satisfy US-03 and FR-07 for `local.reference.admin` or another authenticated user without Booking access.

```
+--------------------------------------------------------------+
| LinerCore                                      User menu v    |
+------------------+-------------------------------------------+
| Navigation       | Breadcrumbs: Home / Booking                |
| > Booking        | h1 Access denied                          |
|                  | You are signed in, but Booking access is  |
|                  | not available for this account.           |
|                  | [Request access] [Back to home]           |
|                  | Decision reference: <id/correlation>      |
+------------------+-------------------------------------------+
```

Rules:

- Denied state remains inside the shell; it must not redirect to a blank standalone page.
- It identifies that the user is authenticated but unauthorized.
- It never implies non-mounted modules are available.

## Screen F - User Menu and Signed Out

Purpose: satisfy US-03 and FR-08.

User menu contents:

- Display name and subject summary.
- Session-safe links only.
- Sign out action as the final destructive/session-ending command.

Signed-out state:

```
[User menu: Sign out] -> [Session cleared] -> [Signed out]
                                           -> [Open protected route]
                                           -> [Redirect to sign-in]
```

Rules:

- Focus returns to a stable signed-out heading after sign-out.
- Protected shell and Booking routes require sign-in after sign-out.
- No stale shell chrome may keep calling Booking APIs.

## Scope Guards

- Do not accept a shell that only displays a user name while Booking still sends `local-user`.
- Preserve W0-01 platform/eventing foundation: W2-01 UX may surface correlation/evidence state, but it must not redesign eventing, outbox, messaging, or platform telemetry flows. Any touched W0-01 file needs W2-01-specific justification and targeted verification.
- Preserve W0-02 reference-data completeness: W2-01 may consume existing Booking reference-data lookups through stable public interfaces, but it must not alter reference-data seed/completeness surfaces or migrate the reference-data UI into the shell.
- Preserve W1-01 Booking behavior: Booking list/detail/create/action behavior remains the business surface being mounted; W2-01 changes shell/session context and actor propagation only.
- Preserve W2-02 design-system foundation: W2-01 consumes existing primitives and records gaps; it does not create a broad component or token foundation.
- Do not migrate reference-data, charge, or container movement screens in W2-01.
- Do not hide W1's live-proof waiver; it remains BLOCKED at `compose-start`, not a PASS.
- Apply `requirements.md` Acceptance Criterion 10 during UX implementation review: W0-01, W0-02, W1-01, and W2-02 files are unchanged or touched only with W2-01-specific justification and targeted verification.

## Review

Verdict: NOT-READY

Findings:

1. The UX flow is complete for the W2-01 user journey. The refined packet covers protected entry, authenticated shell landing, mounted Booking list/detail/action, access denied inside the shell, user menu, sign-out, loading, empty, error, denied, success, and missing-subject states. This is sufficient for US-01 through US-04 and FR-01 through FR-08.
2. Testability is mostly strong. The interaction spec gives route candidates, component states, required inputs, evidence fields, responsive behavior, and acceptance-visible states. QA can derive checks for protected redirect, real subject propagation, denied authorization, sign-out/session clearing, correlation id display, and detector 6d hardcoded-auth coverage.
3. Accessibility coverage is ready. The checklist and interaction spec require landmarks, skip link, one visible `h1`, route-focus management, keyboard reachability, visible focus, text status, live regions for async feedback, contrast, no color-only states, mobile drawer keyboard behavior, zoom checks, and screen-reader smoke evidence.
4. W1-01 and W2-02 preservation are explicit. The mockups reject `local-user`, keep the W1 live-proof waiver recorded as BLOCKED at `compose-start`, preserve existing Booking behavior, and defer broad design-system foundation work to W2-02. The packet also avoids W2-02 and W4-01 scope creep by limiting non-mounted modules to placeholders or links.
5. W0-01 and W0-02 preservation are not explicit in the refined mockup packet. Requirements and stories require W0-01 platform/eventing and W0-02 reference-data preservation, but these mockups only name W1-01, W2-02, and the W4-01 module-migration boundary. Engineering could still infer the right boundary from upstream requirements, but this stage gate needs the refined UX artifact itself to carry the prior-work preservation guard.

Required changes:

1. Add an explicit W0-01/W0-02 preservation guard to the refined mockup packet before approval. It should state that W2-01 must not modify platform/eventing or reference-data seed/completeness surfaces except through stable public interfaces or with a W2-01-specific justification and targeted verification, matching `requirements.md` Acceptance Criterion 10.
2. Keep the existing W1 live-proof waiver language and W2-02/W4-01 scope guards unchanged; they are correctly framed and should not be weakened.
